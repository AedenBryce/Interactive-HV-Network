## What to build

Try allowed and prohibited device changes, see the documented model condition that blocks an action, and see unresolved interlocks disable affected controls.

Implement this as a complete model/session/UI/test slice using the approved simulation-session boundary in the parent specification. Synthetic fixtures must be explicitly identified. Real-network interpretations require source evidence or owner confirmation; unresolved facts remain labelled unconfirmed. Successful software tests do not constitute model acceptance.

## Acceptance criteria

- [ ] Represent physical-interlock conditions, their evidence/review status and affected controls separately from an empty rule list.
- [ ] A synthetic fixture explicitly defines breaker/earth-switch interlock conditions; blocked requests are rejected through both the UI and the session interface with an explanation.
- [ ] A rejected request changes no device/source states or connectivity results and is not treated as an accepted action.
- [ ] An unresolved interlock is visibly flagged and disables affected switching, without inventing keys, operating sequences or generic installed-network conditions.
- [ ] Tests verify successful permitted-by-fixture transitions, rejected transitions, unresolved conditions and attempts to bypass the visible controls through the session interface.
